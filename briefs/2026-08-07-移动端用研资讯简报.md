### [AgentBuilder: Exploring Scaffolds for Prototyping User Experiences of Interface Agents]
**来源**：Apple Machine Learning Research / Carnegie Mellon University（Jenny T. Liang, Titus Barik, Jeffrey Nichols, Eldon Schoop, Ruijia Cheng）  
**类型**：方法论  
**是否与动效相关**：否（偏 Agent 体验原型脚手架；对「可见操作预览 / 确认停顿」有交互态设计含义）

**摘要**：Apple 与 CMU 通过需求 elicitation（N=12）与 in situ 原型研究（N=14），把「界面 Agent 体验」拆成设计与巡检两阶段，并落地设计探针 AgentBuilder（图编辑 + 提示词双向同步 + 本地执行检视）。对 AI 产品经理的价值是：把 Agent UX 当成可原型、可巡检的设计对象，而不是只做模型能力演示。

**详细展开**  
- **背景与问题**：LLM 界面 Agent 能点按钮、滚页面，但「用户如何下达意图、如何看懂 Agent 在干什么、如何中途叫停」缺少可复用的原型脚手架；非 AI 工程师很难参与体验设计。  
- **主要发现/方法/功能/观点**：归纳 Agent 体验原型的关键活动与系统能力诉求；AgentBuilder 提供 Prototyping 界面（节点图 + 自然语言扩展提示）与 Execution 界面（本地跑通并检视 UI 动作预览）；研究发现开发者需要更好的「输入/上下文/输出」可解释机制与对底层实现的可见性。  
- **对移动端用研或 AI 产品经理的启示**：用研协议可按「正常执行 / 易错 / 高风险」三场景设计 Wizard-of-Oz 或探针任务；产品侧把「计划可见、确认门、失败回放」写成可验收 checklist。虽非动效论文，但 Agent 在屏幕上的动作预览节奏（快进/停顿/高亮）仍应进入动效 token 讨论。  
- **原文链接**：https://machinelearning.apple.com/research/agentbuilder（arXiv：https://arxiv.org/abs/2510.04452）

### [Animation2Code: Evaluating Temporal Visual Reasoning in Video-to-Code Generation]
**来源**：UC Berkeley（Anya Ji, Abhijith Varma Mudunuri, David M. Chan, Alane Suhr；arXiv:2606.28593）  
**类型**：方法论  
**是否与动效相关**：是（动画视频 → 可执行代码；外观相似度 vs 时序相似度拆分评测）

**摘要**：Berkeley 提出 Animation2Code：1,069 条真实网页动画视频—HTML/CSS/JS 配对基准，用外观相似度与时序相似度两套人对齐指标评测 VLM「看动画写代码」。结论刺眼：模型常能「看起来像」，却很难「动得对」。对掌握移动端动效的价值是：评审与验收必须把 timing/easing/轨迹写成硬指标，不能只看静态截图或「感觉丝滑」。

**详细展开**  
- **背景与问题**：静态 visual-to-code（网页/图表/SVG）进展快，但动画要求同时理解轨迹、相位与时间结构，再离散成程序；现有基准很少把「纯动画」与「可交互网页」分开。  
- **主要发现/方法/功能/观点**：数据集覆盖旋转/位移/缩放/透明度等组合运动；评测拆开 appearance（帧对齐 + 感知相似）与 temporal（轨迹相关）；Gemini / GPT / Claude / Qwen / Llama 等在可执行率与外观上可较高，时序相似度普遍偏低（公开报告上限约 0.31 量级），微调与迭代精修也难关上缺口。  
- **对快速掌握移动端动效的启示**：设计交付物应包含「时长—缓动—交错—循环」规格表，而不只是 MP4；用研/QA 可用「外观对照 + 轨迹/相位对照」双清单验收 Agent/生成式动效；Reduce Motion 降级方案也要有可执行代码路径，避免只删视频。  
- **原文链接**：https://arxiv.org/abs/2606.28593（HTML：https://arxiv.org/html/2606.28593 ；项目页：https://anya-ji.github.io/animation2code-website）

### [ComposeNavMotion：Jetpack Compose 动画导航库（Material motion 预设）]
**来源**：GitHub / Maven Central（saadkhalidkhan/ComposeNavMotion；artifact `composenavmotion` 1.1.0）  
**类型**：工具  
**是否与动效相关**：是（导航过渡 / Material shared axis / container transform / shared element / 无障碍）

**摘要**：开源库把 Compose Navigation 与动画 API 收成可复用层：类型安全路由、全局/单页动画解析优先级、MaterialNavMotion 预设，以及 SharedNavElement。对快速掌握移动端动效的借鉴点：先选「信息关系对应的过渡语法」，再调弹簧参数，而不是每条路由手写一套 Enter/Exit。

**详细展开**  
- **背景与问题**：业务 App 导航动效容易「各写各的」——有的 fade、有的 slide，方向不一致，也常忽略系统动画缩放/关闭设置。  
- **主要功能/观点**：`AnimatedNavHost` 默认动画 + 无障碍配置；解析顺序为页面 → 嵌套图 → 全局 → fade；预设含 `sharedAxisX/Y`、`fadeThrough`、`containerTransform`、`modal`；支持 `directionAware()`（前进/返回镜像）与共享元素；可尊重系统 animator duration scale 或整体关闭动画。  
- **对快速掌握移动端动效的启示**：用一张表映射路由关系→预设（同级 fadeThrough、父子 sharedAxisY、详情 containerTransform）；用研对比任务里固定「前进/返回成对」样本；Reduce Motion 时保留空间隐喻的静态布局变化，去掉弹跳。证据层级为工程库能力说明，非受控实验。  
- **原文链接**：https://github.com/saadkhalidkhan/ComposeNavMotion

### [Amie Actions Morph]
**来源**：60fps.design / Amie（页面收录时间戳 2026-08-05 UTC）  
**类型**：案例研究  
**是否与动效相关**：是（弹簧 morph / 快捷操作栏展开收合 / stagger）

**摘要**：生产力 App Amie 在底部紧凑 pill 上点「+」，容器以弹簧物理拉伸为宽操作条（Event / Email / Todo），图标与文案交错淡入滑入；关闭则反向 morph。对掌握移动端动效的借鉴点：把「空间占用变化」做成可逆的单一形态变换，而不是弹出第二层遮罩。

**详细展开**  
- **背景与问题**：底部快捷入口若直接弹菜单，容易遮挡内容并打断拇指动线；若只换图标，又缺少「模式已切换」的空间线索。  
- **主要发现/方法/功能/观点**：showcase 强调高响应弹簧、容器形变回弹、子项 stagger；正向/反向共用同一 morph 语法，降低学习成本。  
- **对快速掌握移动端动效的启示**：练习题：用单一 `shape/bounds` 动画驱动「收—展」，子元素只做 opacity/translate 延迟；用研可问「用户是否理解自己仍在同一 dock」。高频路径建议短阻尼、低位移；Reduce Motion 下直接切布局、保留图标位。注意：60fps 为演示收录，非 A/B 结论。  
- **原文链接**：https://60fps.design/shots/amie-actions-morph

### [Amie Search Sheet]
**来源**：60fps.design / Amie（页面收录时间戳 2026-08-05 UTC）  
**类型**：案例研究  
**是否与动效相关**：是（底栏搜索 sheet / 系统键盘同步 / 紧弹簧）

**摘要**：同一 App 的搜索路径：点底栏搜索图标，搜索 sheet 上滑的同时系统键盘同步升起，暗色输入区即时可用。对掌握移动端动效的借鉴点：把「面板入场」与「IME 入场」当成同一编排，消除先后到达造成的跳动。

**详细展开**  
- **背景与问题**：sheet 与键盘若各自动画、不同步，会出现内容被顶两次或短暂空白，搜索「即开即用」的感知会被破坏。  
- **主要发现/方法/功能/观点**：showcase 描述紧弹簧、低延迟；sheet 与键盘同相上移，形成单一连续动作。可与同日 Amie Actions Morph 对照：一个做形态扩展，一个做层叠揭示。  
- **对快速掌握移动端动效的启示**：动效验收加一项「IME 同步」：在真机录屏看 sheet 顶边与键盘顶边是否同帧对齐；用研任务计时从 tap 到首字符可输入。Reduce Motion 时仍应保证键盘与 sheet 终态布局正确，可去掉弹性过冲。  
- **原文链接**：https://60fps.design/shots/amie-search-sheet

### [Liquid Glass Is Cracked, and Usability Suffers in iOS 26]
**来源**：Nielsen Norman Group（Raluca Budiu；专家相关：NN/g / 与 Kate Moran 同机构方法论线）  
**类型**：专家观点/动态  
**是否与动效相关**：是（「无意义动效」批判 / 控件自嗨动画 / 可预测性）

**摘要**（专家相关｜NN/g）：NN/g 系统批评 iOS 26 Liquid Glass：半透明叠层伤可读性，按钮/Tab「为动而动」抢注意，目标变小且控件显隐不稳定。对掌握移动端动效的借鉴点：动效必须回答「帮用户完成什么」，重复触发的装饰运动会从 delight 变成 distraction。

**详细展开**  
- **背景与问题**：系统视觉语言强调折射、涟漪与活力，但日常任务需要的是可扫读、可点准、可形成肌肉记忆的界面。  
- **主要发现/方法/功能/观点**：文章列举透明控件淹没内容、动画按钮反复抢焦点、Tab/搜索布局拥挤、前进键等控件情境显隐破坏可预测性，以及返回面包屑弱化等可发现性回退。结论偏向「景观优先于可用性」。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：用研可设「第 1 次 vs 第 20 次」同一微交互主观负荷；动效规范写明「高频控件禁止循环自嗨」；表达性设计（更大对比、更强层级）不等于更多无触发动画。可与 Material Expressive「运动服务层级」对照阅读。  
- **原文链接**：https://www.nngroup.com/articles/liquid-glass/

### [Designing AI Agents: 4 Lessons from China’s Qwen Agent]
**来源**：Nielsen Norman Group（专家相关：NN/g；远程可用性，中国参与者 N=6）  
**类型**：专家观点/动态  
**是否与动效相关**：否（Agent 下单/订票流程可用性；对「状态可见与确认」有交互启示）

**摘要**（专家相关｜NN/g）：NN/g 远程可用性观察阿里通义 Qwen Agent 的点外卖/票务等任务，提炼四课：冗余入口提升可发现性、复用熟悉 GUI 降学习成本、个人数据最小必要展示、透明定价与关键信息以保护自主。对 AI PM 的价值是：Agent 能力再强，基础可用性债仍会直接杀死信任。

**详细展开**  
- **背景与问题**：用户仍把聊天机器人当成「问答」而非「代下单」；生态型 Agent 虽有数据与履约优势，但首次任务极易卡在心智模型与隐私惊吓。  
- **主要发现/方法/功能/观点**：多数参与者默认打开传统外卖 App；预填 prompt 在宽类别（餐饮）易错配；进入「像外卖 App」的浏览页后信心回升；地址过早完整曝光引发「被泄露」感；价格跳变与行李额缺失导致弃用。  
- **对移动端用研或 AI 产品经理的启示**：评测集应覆盖「发现入口—授权—比价—支付确认」全链路；移动端可用底部任务清单 + 熟悉列表模式承接 Agent 结果；高风险步骤强制可见确认，避免静默假设。  
- **原文链接**：https://www.nngroup.com/articles/designing-ai-agents/

**类型**：专家观点/动态

### [2026 Mobile System Multitasking Capability Comparison：ColorOS 16 / HyperOS 3 / iOS 26]
**来源**：xgamemart 汇总国内横评视角（ColorOS 16、HyperOS 3、iOS 26）  
**类型**：移动设备竞品分析  
**是否与动效相关**：是（跨 App 切换「无缝渲染」叙事 / 系统动画连贯性 / 多任务窗口动线）

**摘要**：横评从多任务流畅、后台保活与 AI 联动对比三系：ColorOS 16 强调「极光引擎」统一无缝架构与切换动画连贯；HyperOS 3 突出超级岛与一步直达缩路径；iOS 26 以稳定与生态连续为主、Liquid Glass 偏视觉。对动效学习：把「切换是否可感知断裂」列为竞品协议项，而不仅看单帧美观。

**详细展开**  
- **背景与问题**：用户真实负荷是会议+文档+消息并行；系统差异越来越体现在切换代价、后台恢复与跨设备接力，而非单应用内页动效。  
- **主要发现/方法/功能/观点**：材料援引厂商数据称 ColorOS 在点击响应、滚动稳定、长期后台保活等有量化宣称，并描述跨屏协同；HyperOS 以信息岛与 AI 直达减步数；iOS 强调长期流畅与 Continuity。需注意：部分数字来自官方/转述，宜用自建任务脚本复测。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：竞品脚本建议录「微信→相册→笔记拖图」三跳切换，编码「有无视觉断裂、有无重载闪白、键盘/浮层是否残留」；动效 token 可区分「系统级共享元素切换」与「应用内微交互」。证据层级为媒体综述，非实验室 FPS 标定。  
- **原文链接**：https://www.xgamemart.com/blog/2026-mobile-system-multitasking-capability-comparison-review-coloros-16-hyperos-3-ios-26-which-is-st.html
