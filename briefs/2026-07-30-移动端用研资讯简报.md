### [Usability — applying M3 Expressive]
**来源**：Koder Design（kds.koder.dev；引用 Google M3 Expressive / 46 项研究）  
**类型**：方法论  
**是否与动效相关**：是（动效规范 / 表达性设计 / motion 强调向量）

**摘要**：在 Google「可用性未封顶 / Expressive」研究叙事之外，Koder 把表达性落地为可审计规范：5 级强调阶梯 × 5 个向量（色/形/尺寸/运动/容器），并强制 AAA 对比度与 `prefers-reduced-motion` 回退。对动效学习的价值是：把「弹不弹、overshoot 多少」写进强调等级，而不是凭感觉加弹簧。

**详细展开**  
- **背景与问题**：业界常把 Expressive 当成「更大按钮 + 更花颜色」；一旦整屏都强调，反而损害扫视与完成率。CHI/Google 侧研究仍在近期滑窗，本期不重推原论文，而收录可执行的应用层规范。  
- **主要发现/方法/功能/观点**：强调阶梯为 subtle → standard → emphasized → hero → critical；运动向量从无动画 → standard → spring → expressive overshoot。规范要求每屏通常最多 1 个 hero；引用 Google 发现「克制强调约 +12% 完成、全面强调约 −8%」。Reduced-motion 下 hero 入场变瞬时、形变循环静态化、hover scale 关闭。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：用研可把「强调密度」做成可测变量（每屏 hero/emphasized 计数）；动效评审清单可对齐五向量——关键 CTA 才允许 expressive spring，次要区只用 standard 或 Effects。落地 token：`emphasis=hero` 绑定 Spatial spring；`subtle` 绑定 0 motion。  
- **原文链接**：https://kds.koder.dev/en-US/reference/foundations-usability.html

### [Turing Test on Screen: A Benchmark for Mobile GUI Agent Humanization]
**来源**：arXiv / 上海交通大学 · CMU（Jiachen Zhu, Lingyu Yang, Weinan Zhang, Jianghao Lin 等）  
**类型**：方法论  
**是否与动效相关**：是（触控运动学 / MotionEvent·SensorEvent / 拟人手势轨迹）

**摘要**：提出「屏幕上的图灵测试」：平台检测器与 GUI Agent 的 MinMax 对抗。基于高保真移动触控与传感器轨迹数据集，发现朴素 LMM Agent 因运动学不自然极易被识别；并建立 Agent Humanization Benchmark（AHB）量化「拟人度 vs 任务效用」权衡。

**详细展开**  
- **背景与问题**：Agent 研究多盯效用与抗干扰，却忽略「Detect vs Anti-Detect」；平台若先区分人机再拦截，会误伤真实用户（如跨 App 自动化触发风控）。  
- **主要发现/方法/功能/观点**：把逻辑动作（tap/swipe）映射为细粒度 Motion/Sensor 事件；用检测指标评估轨迹可区分性；提出从启发式噪声到数据驱动行为匹配的 humanization 模块，并宣称可在不明显牺牲成功率的前提下提升拟人度。代码与数据已公开。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：Agent 评测应单列「触控速度曲线、落点方差、间隔节奏」；产品侧若做 Computer Use，应用研采集真实 MotionEvent 作为对照基线。动效启示：跟手弹簧、可打断手势与自然减速，不只服务观感，也是「像人」的行为特征——与 Log2Motion 的肌骨代价视角互补（昨推，本期不重述）。  
- **原文链接**：https://arxiv.org/abs/2604.09574

### [AgentLens: Adaptive Visual Modalities for Human-Agent Interaction in Mobile GUI Agents]
**来源**：arXiv（Jeonghyeon Kim, Byeongjun Joung, Sunjae Lee 等）  
**类型**：方法论  
**是否与动效相关**：否（但与「即时可视反馈 / 叠加层转场 / 任务关键时刻介入」强相邻）

**摘要**：通过迭代式形成性研究，刻画移动 GUI Agent 的视觉交互设计空间：用户偏好「默认后台执行 + 决策关键点即时可视」；系统在 Full UI / Partial UI / GenUI 三模态间自适应切换。21 人对照中 85.7% 更偏好 AgentLens，PSSUQ 与采用意愿最高。

**详细展开**  
- **背景与问题**：前台执行透明但挡多任务；后台执行可并行但黑盒。单一可视化无法覆盖所有任务。  
- **主要发现/方法/功能/观点**：提炼三原则——非侵入叠加、决策关键点才介入、按任务自适应模态；扩展 speak/ask 动作并绑定可视化选项；用 Virtual Display 支持后台镜像与局部裁剪。GenUI 可按自然语言规格生成精简确认界面。  
- **对移动端用研或 AI 产品经理的启示**：Agent 产品应把「何时露脸、露多少」写成可测交互策略，而非永远全屏镜像。动效相邻：Partial/GenUI 弹出应用短时 Spatial spring + 可打断关闭；Reduce Motion 时改为瞬时叠加与静态高亮，避免持续模糊动画。  
- **原文链接**：https://arxiv.org/abs/2604.20279

### [Motion with Intent: How Animation Earns Its Place in Mobile UI]
**来源**：Tubik Studio（tubikstudio.com）  
**类型**：方法论  
**是否与动效相关**：是（动效方法论 / 微交互功能分类）

**摘要**：主张先问「这段运动在做什么工」，再谈怎么做。把移动端动效拆成导航空间、反馈状态、等待进程、情绪品牌四类，并给出 200–400ms、流程先行、一致性优先、`prefers-reduced-motion` 必做等落地原则。

**详细展开**  
- **背景与问题**：动效常被当作调味料掩盖交互不清晰；结果是到处弹跳却无信息增量。  
- **主要发现/方法/功能/观点**：共享元素转场把关系可视化；点按反馈用约 100ms 缩放补回触控「物理确认」；等待态要传递「系统在干活 / 进度大致在哪」且避免假进度条；品牌庆祝必须绑在真正完成的节点。工具上区分 Lottie（线性矢量）与 Rive（可交互状态机）。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：用研脚本可对每段动画做「功能标签」编码（解释/确认/导航/等待/情绪），统计无效动效占比。快速掌握动效：先画完整用户旅程再标动画点；同交互同缓动；超过 400ms 默认砍。  
- **原文链接**：https://tubikstudio.com/blog/motion-with-intent-ui-animation-mobile/

### [Avec Email Clean Stack Up Timeline Animation]
**来源**：60fps.design / Avec（页面时间戳 2026-07-28 UTC）  
**类型**：案例研究  
**是否与动效相关**：是（Counter ticker / Recap 序列 / Bottom Sheet 揭示）

**摘要**：清理邮件后的「战绩复盘」：计数器与身高尺快速上滚，用蜗牛→霸王龙等尺度比喻强化数量感，末端减速落入可分享的 bottom sheet。示范如何把抽象统计做成可读的运动叙事。

**详细展开**  
- **背景与问题**：清理类任务完成后若只弹静态数字，成就感弱且难传播。  
- **主要功能/观点**：Tap 启动垂直序列；ticker + 插画对照滚动；终点 spring 减速并揭示总结 sheet。标签含 Counter、Gamification、Recap、Ticker。  
- **动效启示**：复盘动效应用「快滚扫视 + 末端可读减速」两段节奏；分享 CTA 放在减速完成后。Reduce Motion：直接展示最终数字与静态对照图。来源为展示站，无对照实验。  
- **原文链接**：https://60fps.design/shots/avec-email-clean-stack-up-timeline-animation

### [Pico Cam Shake and Swipe Coach Mark Animation]
**来源**：60fps.design / Pico Cam（页面时间戳 2026-07-28 UTC）  
**类型**：案例研究  
**是否与动效相关**：是（拟物显影 / 手势教练 / 下滑返回）

**摘要**：宝丽来式显影过程用「晃动手势插画」教学，权限弹窗后再用下滑 coach mark 引导回红色主相册。适合学习「权限后的二次引导」如何用动效接力，避免用户卡在结果页。

**详细展开**  
- **背景与问题**：拟物相机拍完后，用户可能不知道要摇、要滑；系统权限弹窗会打断心智，需要二次引导。  
- **主要功能/观点**：未显影照片逐渐出彩；动画手提示 shake；授权后下方出现 swipe-down coach mark 回到 gallery。标签含 Onboarding、Permissions、Skeuomorphic、Wiggle。  
- **动效启示**：coach mark 应短循环、可跳过；shake/wiggle 对前庭敏感用户需提供关闭。与昨期 Pico 下拉相机同一产品线，可对照「唤出工具」与「结果回流」两段手势语法。

### [Lottie vs. Rive: Optimizing Mobile App Animation]
**来源**：Callstack（工程实践博文；文内基准线索约 2026-06）  
**类型**：工具  
**是否与动效相关**：是（Lottie / Rive 选型与性能）

**摘要**：面向 React Native / 移动端团队比较 Lottie 与 Rive：Rive 以状态机 + 输入触发适合多步 onboarding 合一文件，体积常显著更小；Lottie 适合线性、AE 工作流成熟的展示型动画。强调用 FPS/CPU/内存实测而非观感选型。

**详细展开**  
- **背景与问题**：同一 onboarding 若拆成多个 Lottie JSON，包体与切换逻辑成本上升；交互型动效用线性播放难以跟手。  
- **主要发现/方法/功能/观点**：Rive 编辑器支持实时定制与 trigger；案例称可用单文件覆盖多步；对照同内容时 Rive 文件可远小于 Lottie。文内给出 RN 侧对比思路与官方 runtime 路径。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：工具选型表：庆祝/插画 → Lottie；跟手、多状态、可打断 → Rive。用研验收加「中断手势是否仍顺滑」「低端机掉帧」两栏。  
- **原文链接**：https://www.callstack.com/blog/lottie-vs-rive-optimizing-mobile-app-animation

### [iOS 26 Vs One UI 8.5: Apple Gets Smarter, Samsung Stays Flexible]
**来源**：Cashify / Surbhi Verma（更新于 2026-06-10）  
**类型**：移动设备竞品分析  
**是否与动效相关**：是（Liquid Glass 弹簧动画 vs One UI 速度取向）

**摘要**：媒体横评对比 iOS 26 Liquid Glass「更丝滑、更视觉」与 One UI 8.5「更快、更可定制」：Apple 强调半透明材质与 springy 转场；Samsung 强调启动/多任务响应与动画优化。适合用研把「观感流畅」和「任务吞吐速度」拆成两套指标。

**详细展开**  
- **背景与问题**：用户常把「好看的动画」等同于「系统更快」，导致竞品结论混淆。  
- **主要发现/方法/功能/观点**：iOS 26 视觉改动更大（Liquid Glass、浮动控件、动态效果）；One UI 8.5 偏 refinement（更干净动画、单手底栏、多窗口/DeX）。文中概括为 iOS 更 smooth、One UI 更 snappy；AI 上 Apple 偏隐私整合、Galaxy AI 工具面更广。属媒体体验文，非实验室对照。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：竞品测试分开记录：转场时长主观分、任务切换客观耗时、Reduce Transparency/Reduce Motion 下的可读性。动效策略上，表达性材质需配套性能预算，否则会被感知为「变慢」。  
- **原文链接**：https://www.cashify.in/ios-26-vs-one-ui-8-5-apple-gets-smarter-samsung-stays-flexible

### [Vibe Architects: Agentic Vibe Coders]
**来源**：Nielsen Norman Group / Kate Moran（与 Sarah Gibbons；2026-06-19）  
**类型**：专家观点/动态  
**是否与动效相关**：否（Agent 产品可用性 / 学习路径；与「可打断权限流」相邻）

**摘要**：专家相关（Kate Moran，NN/g）。定性研究观察非开发者如何用 Claude Cowork/Code 等拼装复杂 Agent 工作流，称之为「vibe architects」：能力靠海量试错与社群传播，产品内 onboarding 失败，系统易漂移衰变；结论是 Agent 产品缺的是可用入口而非算力。

**详细展开**  
- **背景与问题**：厂商押注非开发者市场，但工具仍像学徒制黑盒；用户连 Cowork vs Code 边界都搞不清。  
- **主要发现/方法/功能/观点**：参与者每天数小时浸泡；主要学习渠道是 Twitter/Reddit/YouTube 而非产品文档；常不读就点 Accept 授权；系统几周后「decay」需重建。直觉积累但不结晶为可陈述知识，并伴随「我用得不专业」的内疚。  
- **对移动端用研或 AI 产品经理的启示**：Agent PM 应优先设计可观察的状态、权限分级默认与防衰变机制（单一事实源、漂移告警）；用研招募「非开发重度用户」验证 onboarding。动效相邻：连续权限弹窗造成「腕管式狂点」——把高风险动作用更强运动对比/确认节奏，低风险自动通过，减少无效微交互。  
- **原文链接**：https://www.nngroup.com/articles/vibe-architects/
