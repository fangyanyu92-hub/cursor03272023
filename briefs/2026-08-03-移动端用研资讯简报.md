### [Mapping the Design Space of User Experience for Computer Use Agents]
**来源**：Apple Machine Learning Research（IUI ’26；Ruijia Cheng, Jenny T. Liang, Eldon Schoop, Jeffrey Nichols）  
**类型**：方法论  
**是否与动效相关**：是（Agent 动作可见性 / 过程预览与介入节奏的表达层）

**摘要**：针对「Computer Use / UI Control Agents 能力狂奔、UX 设计空间却几乎未成图」的缺口，Apple 团队用两阶段形成性研究给出 taxonomy：User query、Explainability、User control、Mental models。N=8 从业者访谈迭代 + N=20 Wizard-of-Oz 验证。对动效学习的价值是：把「高亮点按、轨迹跟随、下一步预览、可打断确认」写成可调度的过程表达，而不是事后贴一层 Loading。

**详细展开**  
- **背景与问题**：LLM/MLLM Agent 已能点按钮、滚页面，但多数工作停在模型与基准；用户如何提问、如何看见 Agent 在干什么、何时能插手、如何建立心智模型，缺少系统地图。  
- **主要发现/方法/功能/观点**：Phase 1 复盘 9 个 2024–2025 公开展示的桌面/浏览器/移动 Agent，提炼初始分类，再与 UX/AI 从业者共创；Phase 2 由研究者扮演浏览器 Agent，在正常、易错与高风险任务中探测反应。taxonomy 覆盖查询表达层级与模态、活动可见性/可保留性、行动描述、推理透明度、下一步预览、运行时状态、暂停/确认/接管等控制点，以及能力边界与错误恢复相关的心智模型。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：用研脚本可按四象限建检查表——Query（意图是否可修正）、Explain（当前步骤是否在屏幕上「被看见」）、Control（风险步骤是否有确认拍）、Mental model（结束后用户能否复述「Agent 做了什么」）。动效 token 建议：`agent_focus`（强对比指向当前控件）、`agent_step`（短可打断位移）、`agent_confirm`（风险动作前的停顿 settle）、`agent_undo`（撤销回弹）。Reduce Motion：保留高亮与文案差分，去掉表演性轨迹。  
- **原文链接**：https://machinelearning.apple.com/research/mapping（arXiv：https://arxiv.org/abs/2602.07283 ；ACM：https://doi.org/10.1145/3742413.3789132）

### [Magical Touch: Transforming Raw Capacitive Streams into Expressive Hand-Touchscreen Interaction]
**来源**：Microsoft Research（CHI 2026 Extended Abstracts；Yuan Guo, Xizi Gong, Yizhong Zhang, Xiaoyu Zhang）  
**类型**：方法论  
**是否与动效相关**：是（表达性触控 / 物理仿真响应 / 接触几何与压力驱动运动）

**摘要**：主流触摸屏把大面积手掌/手侧接触当噪声滤掉，手的表达潜力被浪费。Magical Touch 把原始电容传感流直接接回交互环，让手形几何与接触强度实时驱动屏幕对象的物理响应。对掌握移动端动效的启示：运动参数可从「手指轨迹」升级为「接触场」——形状、面积、压力成为可设计的输入维度。

**详细展开**  
- **背景与问题**：电容屏为了稳定多点触控，长期丢弃大面积接触；交互仍困在指尖点击与少量手势词汇，难以承载连续、具身的表达。  
- **主要发现/方法/功能/观点**：方法直接消费 raw capacitive streams，在现有触摸硬件上支持任意手势形态；以物理引擎驱动的互动游戏做可行性演示，覆盖单人、多人协作与压力敏感模式，展示对象如何对接触几何与强度做实时响应。结论强调：这是比指尖范式更连续、更具身的触控设计空间。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：评测「表达性微交互」时，除点击成功率外，可记录接触面积变化、压力梯度与对象弹簧响应是否可读。落地时先把压力/面积映射到现有 motion token（如 `spatial` 位移 vs `effects` 透明度），避免把压力抖动直接绑到 alpha 造成闪烁。可访问性：提供「仅指尖模式」回退，避免手掌误触；前庭敏感用户需可关物理抖动。  
- **原文链接**：https://www.microsoft.com/en-us/research/publication/magical-touch-transforming-raw-capacitive-streams-into-expressive-hand-touchscreen-interaction/

### [MoMo: Dial Motion Mode in Robot Manipulation with Spatiotemporal Action Tokenization]
**来源**：Apple Machine Learning Research（2026-07；arXiv:2607.26315；Yuhan Hu 等）  
**类型**：方法论  
**是否与动效相关**：是（motion mode / 时空解耦的节奏与路径 / 可迁移运动方言）

**摘要**：提出把「怎么做」（motion mode）从「做什么」（task）里拆出来：空间码管路径与接触，时间码管节奏、加减速与犹豫。连续 scaler 可在稳态/动态原型间插值，且能迁移到从未以该模式演示过的任务。对 UI 动效体系的迁移价值极高——把「快/稳/弹」做成跨场景可复用的设计因子，而不是每个页面各写一套曲线。

**详细展开**  
- **背景与问题**：模仿学习常把行为风格与任务绑死；换任务就要重新演示同一种「手感」，无法像旋钮一样调节执行气质。  
- **主要发现/方法/功能/观点**：两阶段框架——Stage 1 用并行 RVQ 把动作块编成空间/时间码；Stage 2 行为克隆 Transformer 条件于任务 ID + 连续 motion-mode scaler。六项真机任务上，人类评分员可区分稳态/动态/中间态；在单模式演示的 held-out 任务上仍能迁移所请求模式并大体保持成功率。潜空间中空间码偏任务、时间码偏模式。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：设计系统可显式定义 `motionMode = {steady, standard, expressive}`，分别绑定 M3 Spatial/Effects 或 iOS spring 参数；关键 CTA 用 expressive，列表重排用 steady。用研可做「同一任务、三种节奏」对照：完成时间、误触、主观「是否可控/是否夸张」。Agent UI 也可把 scaler 暴露为用户偏好（谨慎模式 vs 利落模式）。Reduce Motion：强制 steady + 取消 overshoot。  
- **原文链接**：https://machinelearning.apple.com/research/momo-motion-mode-manipulation（arXiv：https://arxiv.org/abs/2607.26315）

### [Rewriting Rive React Native with Nitro Modules: up to 94× Faster Multi-View Loads]
**来源**：Margelo Blog / Miklós Fazekas（与 Rive 合作；2026-07-09）  
**类型**：工具  
**是否与动效相关**：是（Rive 运行时 / 移动端多实例动效性能 / 数据绑定）

**摘要**：把 Rive React Native SDK 从「视图吞掉一切状态」的旧桥架构，重写成 Nitro HybridObjects：`RiveFile`、View Model、属性成为可持有、可共享的对象。iPhone 13 mini 实测：24 个视图加载同一 2.9MB 文件约 29ms vs 旧版 ~2716ms（约 94×）；内存约 4.7× 更省；属性写入约 3.2× 更快。对动效落地的关键点：复杂状态机动画终于能在列表/多卡片场景「先预加载、再多处复用」。

**详细展开**  
- **背景与问题**：旧 RN 模块模型是单例扁平 API，无法自然表达 Rive 的对象图；文件被困在每个 View 内重复解析，多实例场景卡顿与内存暴涨。  
- **主要功能/观点**：Nitro 暴露真实对象生命周期与类型化 API；支持预加载、跨 View 共享文件、首帧前完成 data-binding（避免默认态闪一下）。基准含多视图展示、内存足迹、属性写入、加载/释放；配套 on-device harness 测试。新包 `@rive-app/react-native`（Nitro）与旧 `rive-react-native` 并行迁移。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：验收「动效是否可产品化」时，除观感外加三项性能门槛——首屏多 Lottie/Rive 实例的 TTI、滚动中掉帧、主题/分数绑定是否无闪烁。用研可对比「装饰性一次性播放」vs「数据驱动状态机」在理解任务状态上的差异。与 Callstack「Lottie vs Rive」讨论互补：选型不只看编辑器，还看运行时对象模型是否扛得住列表密度。  
- **原文链接**：https://blog.margelo.com/rewriting-rive-react-native-with-nitro-modules

### [Swiggy Q AI Chat Logo Animation]
**来源**：60fps.design / Swiggy（页面收录；交互标签含 AI / Morph / Chat）  
**类型**：案例研究  
**是否与动效相关**：是（AI 助手入口 Morph / 建议 Chip 错落入场）

**摘要**：点按 AI 助手入口后，深色聊天界面自右侧滑入；中央 Q Logo 经历圆角方→旋转四角星→字母 Q 的连续 morph，问候文案淡入，建议 Chip 自右错落滑入。示范「AI 人格出场」如何用一段可读的形态变化建立模式切换，而不是生硬切页。

**详细展开**  
- **背景与问题**：外卖/本地生活 App 把 AI 助手塞进原有导航时，用户常分不清「我还在点餐」还是「我已进入对话模式」。  
- **主要功能/观点**：入口→聊天的空间过渡（右滑）+ Logo 身份变形 + Chip 建议的 stagger，构成「召唤助手」的三拍叙事；标签强调 AI、Assistant、Chat、Morph、Slide。  
- **动效启示（快速掌握）**：AI 入口动效预算集中在「身份确认」一拍（Logo morph settle 可读后再出 Chip）；建议 Chip 用弱运动、短时长，避免抢主身份。Reduce Motion：跳过星形旋转，保留静态 Q + 列表淡入。来源为展示站，无对照实验。  
- **原文链接**：https://60fps.design/shots/swiggy-q-ai-chat-logo-animation

### [Family Fluid Tab Switch Text Morph Interaction]
**来源**：60fps.design / Family（钱包 App；描述时间戳约 2026-07-24 UTC）  
**类型**：案例研究  
**是否与动效相关**：是（Tab 内容弹簧滑移 / 空状态错落 / 文本 Morph）

**摘要**：在 Tokens 与 Collectibles 之间切换时，内容区水平滑移并淡入淡出；空状态占位卡与说明文字带轻微 spring overshoot 入场，非激活内容滑出，Tab 头激活态平滑过渡。适合学习「同级信息架构切换」如何用共享节奏保持空间记忆。

**详细展开**  
- **背景与问题**：同级 Tab 若硬切，用户会丢失列表滚动位置与「我在哪一类资产」的空间锚点。  
- **主要功能/观点**：水平 slide + fade + spring overshoot 的空状态编排；强调触觉响应式导航，而不是装饰性弹跳。  
- **动效启示**：Tab 切换优先保证方向与手指一致；overshoot 只给空状态插画/文案，列表内容用更短 settle。与昨日 Airbnb Search Tab、Family Continuity 对照：同一产品线的「连续体」方言——Hero morph 用于跨步骤，Tab slide 用于同级切换。Reduce Motion：交叉淡入、取消 overshoot。  
- **原文链接**：https://60fps.design/shots/family-fluid-tab-switch-text-morph-interaction

### [One UI 8.5 vs iOS 26 vs HyperOS 3 vs Pixel Android 16：系统动画横评]
**来源**：Matthews Tech（YouTube；四系统 Animation Test）  
**类型**：移动设备竞品分析  
**是否与动效相关**：是（解锁入场 / 主屏滑动 / 应用抽屉与系统转场体感）

**摘要**：作者在 One UI 8.5（beta）、iOS 26、HyperOS 3 与 Pixel 原生 Android 16 上并排比较系统动画。口述体感大致为：各机主屏滑动都「够顺」，iOS 分页滑动主观偏慢；解锁后图标入场各家方言不同（HyperOS 飞入+涟漪、iOS Face ID 解锁标志衔接等）；应用抽屉上 One UI 动画偏「刻意留时长」。适合做系统级 motion 竞品的分镜脚本，而非实验室帧率结论。

**详细展开**  
- **背景与问题**：旗舰「顺滑」争论常被单机演示绑架；缺四系统同一手势任务的并排对照。  
- **主要发现/方法/功能/观点**：覆盖解锁后图标入场、主屏分页、应用抽屉等常见路径；强调 Pixel 动画长期被作者偏好，同时指出 One UI 8.5 beta 流畅度已可测、部分转场节奏仍偏慢。属创作者体验视频，非仪器采样。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：竞品脚本建议分轨——解锁入场时长、分页滑动跟手/惯性、抽屉手势可发现性、Reduce Motion 开启后的任务耗时。策略上：系统方言一致性（全链路同一物理参数）比单条「更弹」更重要；App 内动效应主动对齐宿主 OS 的快慢预期，避免「系统很快、应用很飘」。  
- **原文链接**：https://www.youtube.com/watch?v=_imrFIfuC5c

### [千问办公硬刚 WorkBuddy，5 轮对比测评后，结果有点意外]
**来源**：人人都是产品经理 / 产品笔记（三哥；2026-07-29）  
**类型**：专家观点/动态  
**是否与动效相关**：否

**摘要**：专家相关（AI 产品经理常驻平台「人人都是产品经理」）。对阿里「千问办公」0.1.0 公测与腾讯 WorkBuddy 做外在能力盘点 + 五轮同提示词实测（网站高保真、移动 App 设计、PPT、深度研报等）。结论倾向：WorkBuddy 功能面与模型开放性更成熟；千问办公在可交互预览网站与 PPT 上有亮点，研究报告与生态广度仍需补课。对 AI PM 的价值是可复用的 Agent 办公竞品评测框架。

**详细展开**  
- **背景与问题**：WorkBuddy 月活传闻达千万级白领用户后，阿里整合 QoderWork/悟空/MuleRun 推出千问办公，桌面办公 Agent 竞争升温。  
- **主要发现/方法/功能/观点**：对比工作台信息架构、IM 远程控制配置、专家/技能/链接器、价格与积分；内在能力上固定提示词比较设计站、冥想 App、PPT、少儿 AI 编程研报。指出模型开放（WorkBuddy 多模型 vs 千问封闭 Qwen）可能是选型关键分歧；设计类任务双方都强，深度研究 WorkBuddy 更专业。  
- **对移动端用研或 AI 产品经理的启示**：做 Agent 产品对比时，把「外在能力地图」与「同提示词交付质量」拆开打分；移动端相关可增测——远程 IM 唤起桌面任务的确认动效、生成物预览的可点击性、错误可撤销。与本期 Apple taxonomy 对照：评测应单列 Explainability（步骤是否可见）与 Control（能否中途接管）。  
- **原文链接**：https://www.woshipm.com/ai/6436882.html
