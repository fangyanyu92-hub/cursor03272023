### [AEP guideline: Physics Based Motion]
**来源**：Android Developers / Apps Experience Program（Google）  
**类型**：方法论  
**是否与动效相关**：是（物理弹簧动效规范 / 可打断过渡 / AEP 验收）

**摘要**：Android Apps Experience Program 把「Physics Based Motion」列为正式体验门槛：核心导航与状态变化禁止 0ms 硬切，鼓励用 spring 取代固定时长缓动，使动效保留手势动量且可被打断。对快速掌握移动端动效的价值是：把「弹簧参数 + 可中断性 + 上下文插值」写成可验收 token，而不是凭感觉调曲线。

**详细展开**  
- **背景与问题**：固定 duration + easing 的转场在快速连点、返回、手势中途改向时容易显得僵硬；瞬时切屏会破坏空间连续性，也削弱「系统跟上了我」的反馈感。  
- **主要发现/方法/功能/观点**：AEP 要求：(1) 主路径导航/状态变化不得出现 0ms 视觉跳变；(2) 核心交互、导航与临时视图须有 >0ms 的可见过渡；(3) 用 cross-fade、标准缓动、shared element 或 spring 等插值保持上下文。Compose 侧提示用 `spring()` 的 `dampingRatio` / `stiffness` 调手感；文档并指向 Dynamic Animation / Spring 教程。适用所有形态，且若 App 在非 Android 平台有对等物理动效实现，亦纳入适用说明。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：评审清单可拆成三问——主路径是否无硬切、手势中断后动量是否连续、关键 CTA 的 Spatial spring 是否强于次要 effects。用研脚本可对比「固定 300ms tween vs spring」在连点/返回任务上的误触、重试与主观「跟手感」。Reduce Motion：保留短淡入淡出与高亮，去掉高弹性 overshoot。  
- **原文链接**：https://developer.android.com/distribute/aep/aep-req-physics-based-motion

### [Scaling Synthetic Task Generation for Agents via Exploration（AutoPlay）]
**来源**：Apple Machine Learning Research（2026-03；Ramrakhya 等）  
**类型**：方法论  
**是否与动效相关**：否（偏移动 Agent 任务合成与评测；探索轨迹含界面状态变迁）

**摘要**：Apple 提出 AutoPlay：先用 MLLM explorer 在真实环境里系统性探索状态与功能，再基于探索轨迹与任务指南提示合成可执行、可验证任务。报告在 20 个 Android App 上生成约 2 万任务、在 13 个 Ubuntu 应用上生成约 1 万任务，并用于训练后使 mobile-use 成功率最高提升约 20.0%、computer-use 约 10.9%，配合 verifier 奖励的 RL 再增约 5.7%。

**详细展开**  
- **背景与问题**：UI Agent 后训练缺「多样、可行、可验证」的下游任务；纯人工标注贵，而仅靠提示、缺少环境 grounding 的任务生成覆盖面窄。  
- **主要发现/方法/功能/观点**：两阶段管线——(i) Exploration：explorer 发现新状态与交互；(ii) Task generation：结合轨迹与 guideline prompts 合成任务，再用 executor + verifier 大规模造演示、少依赖人工。结果强调环境 grounded 任务对 mobile-use / computer-use 迁移的价值。  
- **对移动端用研或 AI 产品经理的启示**：产品评测可借鉴「探索覆盖 × 可验证成功」双指标，而不是只测脚本化 happy path。用研可把真实用户路径沉淀为 task guideline（含异常、权限、中断），再驱动合成回归集。Agent 产品需单独设计「探索期可见性」：用户是否知道 Agent 在试哪些入口、失败后如何回退。  
- **原文链接**：https://machinelearning.apple.com/research/scaling-synthetic-task

### [WhatsApp Usernames Feature Into Animation]
**来源**：60fps.design / WhatsApp（页面时间戳 2026-07-31 UTC）  
**类型**：案例研究  
**是否与动效相关**：是（功能介绍页 idle / 轨道式插画动效）

**摘要**：WhatsApp 用户名功能介绍屏用围绕「@」的虚线轨道与纸飞机、气泡、锁、手势等元素做轻量循环 idle 动效，营造友好、可理解的功能氛围。对掌握移动端动效的借鉴点是：功能宣介页可用「低干扰循环运动」承担注意力与品牌语气，而不抢占主 CTA。

**详细展开**  
- **背景与问题**：新账号标识能力需要在首屏完成「这是什么 / 为何安全 / 下一步」教育；静态插画容易显得冷，强动画又可能干扰阅读。  
- **主要功能/观点**：标签含 Idle Animation、Illustration、Intro、Onboarding、Orbit；中心「@」为锚点，周边元素轻幅浮动形成持续但克制的生命感。来源为动效展示站，无对照实验数据。  
- **对快速掌握移动端动效的启示**：把介绍动效预算压在「背景层」：振幅小、周期慢、可随时被主按钮打断；正文与 CTA 保持静止可读。验收时检查低端机帧预算与 `prefers-reduced-motion`（改为静态插画）。适合作为「营销/教育屏」动效样板，不宜套到高频工具流。  
- **原文链接**：https://60fps.design/shots/whatsapp-usernames-feature-into-animation

### [Airbnb Search Tab Interaction]
**来源**：60fps.design / Airbnb  
**类型**：案例研究  
**是否与动效相关**：是（搜索 Overlay / Tab 指示器 / 表单卡片 morph）

**摘要**：点击搜索栏进入全屏模糊 Overlay；在 Homes / Experiences / Services 间切换时，指示器滑动、图标缩放，底部表单卡片随 Tab 做高度与文案的 morph（如「Who」变为「What」）。示范如何用共享空间里的形态过渡，让「同一搜索任务、不同对象」保持连续心智模型。

**详细展开**  
- **背景与问题**：多品类搜索若整页硬切，用户会重读表单结构；若只改文案不变布局节奏，又可能错过「字段语义已变」的信号。  
- **主要功能/观点**：标签含 Blur、Card、Morph、Spring Physics、Tabs 等；关键技巧是「容器身份连续 + 字段语义交叉淡入」，用高度微调提示结构变化。展示站素材，非受控可用性实验。  
- **对快速掌握移动端动效的启示**：多模式表单优先做 *shared container morph*，而不是平行页面跳转。动效 token 建议：`tab_indicator` 短滑动；`field_swap` 交叉淡入 + 高度 spring；背景 blur 仅在进入 Overlay 时出现一次。用研可测切换 Tab 后首字段定位时间与误填率。Reduce Motion：跳过 morph，直接替换字段标签并加短高亮。  
- **原文链接**：https://60fps.design/shots/airbnb-search-tab-interaction

### [Xiaomi HyperOS 3 vs iOS 26 vs OneUI 8: Which one is best?]
**来源**：XimiTime / Emir Bardakçı  
**类型**：移动设备竞品分析  
**是否与动效相关**：是（系统动画与导航体感 / Liquid Glass / Jelly Effect）

**摘要**：面向 HyperOS 3、iOS 26、One UI 8 的体验横评，从控制中心定制、桌面智能到「Animation and Navigation」专节对比三套系统动效哲学：iOS 偏物理 Jelly / Liquid Glass，HyperOS 追近旗舰流畅但机型分层明显，One UI 更强调速度与一致性而非表现力。适合用研做系统级动效竞品框架，但需注意其为媒体综述而非实验室对照。

**详细展开**  
- **背景与问题**：2025–2026 旗舰竞争已从单一硬件转向 AI、生态与设计语言；动效是用户感知「快/稳/高级」的捷径，却缺少可复用的对比维度。  
- **主要发现/方法/功能/观点**：文中归纳 Apple 以 Liquid Glass 与物理感运动强化情绪与美感（并提到可读性争议与 Tinted Mode）；Samsung 强调可靠、生产力与可定制控制中心，动画偏响应速度；Xiaomi 走 iOS 式视觉 + Android 灵活的混合路线（圆角、Live Blur、HyperIsland），动画在旗舰上接近 iOS，但跨价位机型表现不稳定。来源偏编辑观点，未给出仪器化帧时间或任务完成数据。  
- **对移动端用研或 AI 产品经理的启示（含动效）**：竞品动效研究建议固定任务集（启动 App、控制中心、多任务、返回桌面），同时记录主观流畅度与客观掉帧/触控到首帧；并按高/中/低端机分层，避免只看旗舰 demo。跨端 App 可准备两套运动方言：表现型 spring（接近 iOS/HyperOS 旗舰）与效率型短过渡（接近 One UI）。  
- **原文链接**：https://ximitime.com/xiaomi-hyperos-3-vs-ios-26-vs-oneui-8-which-one-is-best-74735/

### [Why You Need Mentorship and How to Get It Right]
**来源**：Nielsen Norman Group / Evan Sunwall（2026-07-31；专家相关：Kate Moran 所在机构 NN/g）  
**类型**：专家观点/动态  
**是否与动效相关**：否

**摘要**：NN/g 发布关于职业导师制的实操指南：澄清「导师≠管理者/单次咨询」，给出选择内外部导师的利弊、会谈节奏（建议初期每月一次、约一小时）与 mentee 责任清单。对用户研究员与 AI 产品经理，可作为团队成长与跨职能协作（设计–工程–研究）的制度参考。

**详细展开**  
- **背景与问题**：许多人把导师制误认为仅适合新人、或等同于偶发答疑；结果关系浅、建议难落地，双方都觉得浪费时间。  
- **主要观点/方法**：文章区分 mentorship 与 coaching；建议导师比自己高 2～3 级、具备相关行业经验且同时 mentee 不宜过多；强调 mentee 需自带目标、会前议程、会后行动与复盘。并引用学术综述称良好导师制与晋升、薪酬增长、更低 burnout 等相关（组织情境外推需谨慎）。  
- **对移动端用研或 AI 产品经理的启示**：在 Agent/动效等高变化专题上，可建立「专题导师」而非泛泛聊天——例如每月一次带着可用性录像或动效验收单复盘。AI 加速产出后，更需要人类导师帮你校准「什么值得做深、什么只是生成噪音」。  
- **原文链接**：https://www.nngroup.com/articles/mentorship/

### [做出来已经不值钱了：AI 产品真正的分水岭在 1-N]
**来源**：人人都是产品经理（专家相关平台；2026-07-30）  
**类型**：专家观点/动态  
**是否与动效相关**：否

**摘要**：面向 AI 产品经理的平台长文指出：Vibe Coding 让 0-1 商品化后，稀缺性转移到上线后的 1-N。作者提出可落地的三条迭代线——Case 线（把真实使用沉淀为资产）、迭代线（Prompt/Agent 框架分层改）、模型线（换模的回归与灰度成本）——强调「发布即巅峰」是当前最普遍失败形态。

**详细展开**  
- **背景与问题**：公开内容大量停留在「一天做出 Demo」；上线后意图漂移、Prompt 失效、模型升级带来的行为变化缺少操作手册，导致产品停在发布当天的界面与能力。  
- **主要观点/方法**：把 AI 产品时间轴改写为「上线才开始」；Case 线负责收集重问、失败与高价值路径；迭代线明确改 Prompt、工具层还是编排层；模型线用全量回归 + 灰度 + 可回滚衡量换模，而不是追新。论述以作者观察与框架为主，非受控实验。  
- **对移动端用研或 AI 产品经理的启示**：用研应从「上线前验证」延伸为「上线后 case 库运营」：每次关键失败会话打标签（意图漂移 / 检索未召回 / 权限中断 / 动效或状态不可见等），再映射到三条线的改动层级。Agent 类移动产品尤其要把「可观测的失败类型」做成周度评审输入。  
- **原文链接**：https://www.woshipm.com/ai/6436891.html
