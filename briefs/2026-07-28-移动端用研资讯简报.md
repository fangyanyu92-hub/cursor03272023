### [A Task-State Representation for Long-Horizon Mobile GUI Agents]
**来源**：arXiv / 中国人民大学 · 北京航空航天大学（Yujie Zheng, Zikang Liu, Xin Zhao, Ji-Rong Wen；Submitted 2026-07-01）  
**类型**：方法论  
**是否与动效相关**：否（但与「动作前后界面过渡校验 / 状态可视化」产品形态相邻）

**摘要**：长程移动 GUI Agent 常把「持久任务状态」与「瞬时屏幕观察」混在同一 prompt，导致目标漂移、进度幻觉与卡死重试。TSR 用免训练外部状态块（全局摘要 + 子目标进度 + 过渡感知校验）把三者解耦，四基准上最高约 +12 个百分点成功率。

**详细展开**  
- **背景与问题**：主流 thought-action-observation 把指令、截图窗口与历史文本堆叠；步数一长，Agent 会忘初衷、编造已完成步骤，或把 UI 延迟误判为失败而局部循环。  
- **主要发现/方法/功能/观点**：TSR 作为 actor 外层 wrapper：每步用动作前后截图对比更新状态块，再注入下一轮推理；三视图分别为 Global Task-State Summary、Progress Tracker（分解/已完成/当前/剩余）、Transition-Aware Focus（校验上一步是否生效并给出下一步焦点）。在 MobileWorld、AndroidWorld、MemGUI-Bench、VenusBench-Mobile 与两套基座模型上多数配置提升，长程/跨 App 场景收益最大。  
- **对移动端用研或 AI 产品经理的启示**：Agent 评测应单列「目标保持、进度可核验、失败不盲重试」指标，而不是只报端到端成功率；产品侧可把进度轨与「将发生什么」预览做成用户可见的确认层。动效相邻启发：动作前后态对比本身是评测信号——若关键控件缺少可感知过渡，人与 Agent 都会误判「点了没反应」。  
- **原文链接**：https://arxiv.org/abs/2607.00502（HTML：https://arxiv.org/html/2607.00502）

### [How Long Should App Animations Be? The 200ms Rule for iOS & Android]
**来源**：Appy Pie Blog（Last Updated 2026-05-15）  
**类型**：方法论  
**是否与动效相关**：是（动效时长规范 / 平台对照 / 微交互预算）

**摘要**：面向移动端落地的动效时长方法论：默认 200–300ms + ease-out；微交互约 100ms，Hero/模态 300–400ms；并给出 iOS HIG 与 Material 时长对照表，强调 `prefers-reduced-motion`（文中引用 WebAIM 约 35% 用户受益）。对快速掌握移动端动效最直接的价值是「可写入 design token 的时长矩阵」。

**详细展开**  
- **背景与问题**：团队常凭「看起来顺眼」定时长，导致 Tab 切换拖沓、小控件动画过慢、跨平台同一产品「手感」分裂。  
- **主要发现/方法/功能/观点**：四条调参规则——位移越小越短、Hero 可加长、高频操作必须短、超过 500ms 易判「卡」。文内对照：Material 标准转场约 200ms，iOS 模态约 500ms；并区分 ease-out 进场、ease-in 离场、spring 物理反馈。动画被框成三项功能工作：空间定位、掩护加载、确认 affordance——而非装饰层。  
- **对快速掌握移动端动效的启示**：先建三档 token：`micro`（75–150ms）、`standard`（200–300ms）、`hero`（300–400ms），再按平台微调；用研可测「是否误触二次 / 是否感觉慢」而非只问「好不好看」。注意：部分行业对比与平台数字为指南归纳，落地需结合本机 120Hz/Reduce Motion 实测。  
- **原文链接**：https://www.appypie.com/blog/mobile-app-animation-guide

### [FlowEval: Reference-Based Evaluation of Generated User Interfaces]（往期精选）
**来源**：Apple Machine Learning Research / Purdue（Jason Wu†, Priyan Vaithilingam, Eldon Schoop, Jeffrey Nichols, Titus Barik；Apple 站点标注 published July 2026）  
**类型**：方法论  
**是否与动效相关**：否（交互流/导航轨迹评估；可扩展到转场与状态连贯性）  
**首次收录日期**：2026-07-11

**摘要**：往期精选。面对 LLM/编码 Agent 生成 UI「好看但不好用」难评估，FlowEval 用 Computer Use Agent 采集参考站与生成站的交互 trace，再以 DTW / eBLEU / WMD 等参考相似度打分；专家 Arena（429 评分）显示其排序对齐度优于基线 MLLM judge。

**详细展开**  
- **背景与问题**：专家走查准但贵；纯 LLM-as-a-judge 可扩展却不透明、易偏。  
- **主要发现/方法/功能/观点**：从 WebVoyager / REAL 提炼任务，用 coding agent 批量生成 React 对照站，以视觉 CUA（UI-TARS）跑 trace，截图嵌入后算对齐/重叠/分布三类相似度；强调参考集可嵌入企业设计语言与关键流程。  
- **本次新增启发角度**：对照本期 TSR——前者管「Agent 是否记得任务状态」，后者管「生成 UI 是否撑得住真实交互流」；动效落地可将「键盘⇄sheet 接力、共享元素转场」写成必须通过的 reference flow，把掉帧/硬切直接计为 trace 偏离。  
- **原文链接**：https://machinelearning.apple.com/research/floweval-ui-evaluation（arXiv：https://arxiv.org/abs/2605.04165）

### [Linear Issue Actions Popup Interaction]
**来源**：60fps.design / Linear（页面时间戳 2026-07-27 UTC）  
**类型**：案例研究  
**是否与动效相关**：是（Bottom Sheet / 键盘接力 / Spring 转场）

**摘要**：Linear 移动端在工单创建流中，点 Priority/Team/Labels 时系统键盘下滑、自定义 Bottom Sheet 上滑接力；选完或关闭后 sheet 退下、键盘回升，形成无布局跳动的「输入态⇄选择态」节奏。适合学习移动端表单里高频控件切换的动效编排。

**详细展开**  
- **背景与问题**：元数据选择若突然切页或硬切键盘，会打断打字心智并造成跳动。  
- **主要功能/观点**：键盘与 sheet 反向滑移、时长对齐，用 spring 保持连续感；交互标签含 Bottom Sheet、Picker、Spring Physics。  
- **动效启示**：把「键盘占用高度」与「sheet 入场」做成互斥且可打断的一对 token；Reduce Motion 下降级为瞬时替换 + 静态 sheet。来源为展示站，无可用性实验数据。  
- **原文链接**：https://60fps.design/shots/linear-issue-actions-popup-interaction

### [Apple Wallet Card Gyro Pattern Color Change Interaction]
**来源**：60fps.design / Apple Wallet（页面时间戳 2026-07-27 UTC）  
**类型**：案例研究  
**是否与动效相关**：是（Gyroscope / 设备姿态驱动 / 拟物材质反馈）

**摘要**：Apple Cash 卡设置流程中，密集点阵全息纹理随设备倾斜在金绿→蓝紫→暗单色间连续变色，模拟箔片反光。示范「硬件姿态 → 材质参数」的微交互如何强化金融产品的触感与可信度。

**详细展开**  
- **背景与问题**：静态卡面预览难以传达「实体卡/支付介质」的质感与贵重感。  
- **主要功能/观点**：陀螺仪驱动色相/亮度连续映射，运动即反馈；属 Setup 场景下的品牌签名动效。  
- **动效启示**：姿态驱动动效应设采样节流与低功耗路径；无陀螺仪或 Reduce Motion 时保留静态高光帧。用研可问「是否感觉更像真卡/更信任」，而非只测美观偏好。  
- **原文链接**：https://60fps.design/shots/apple-wallet-card-gyro-pattern-color-change-interaction

### [Liquid Glass vs Material 3 Expressive: the Two Interface Languages Redefining 2026]
**来源**：Beryl Design（Guillaume Hambourger；2026-07-23）  
**类型**：移动设备竞品分析  
**是否与动效相关**：是（Liquid Glass 深度折射 vs M3 Expressive 弹簧 / Spatial·Effects）

**摘要**：横评 2026 两大系统语言：Apple 在 WWDC 叙事上巩固 Liquid Glass 并转向稳定与端侧 AI；Google 以 `motionScheme` 把运动升为与色/字同级的系统变量，区分 Spatial（位姿尺寸、可 overshoot）与 Effects（色/透明度、避免抖动）。对动效学习的价值是直接给出可落地的双轨 token 分工。

**详细展开**  
- **背景与问题**：扁平收敛结束后，跨端「一套视觉」失效；设计师需在克制材质 vs 情绪化弹簧之间做产品级选择。  
- **主要发现/方法/功能/观点**：文中综合系统解读、动画引擎深潜与 Pixel 10 实测：M3 Expressive 通知滑动带物理粘滞与触觉，音量条强度随档位变化；同时指出 Play Store/Maps 等三方应用尚未全面跟上，adoption 是 Google 路线的风险。Apple 侧则靠系统强制统一，代价是视觉叙事放缓。  
- **启示（含动效）**：设计系统文档应并列 Standard/Expressive（或 sober/expressive）两套 motion scheme；空间属性与特效属性分曲线；触觉升格为设计物料。证据边界：本文为视频综合二次写作，非受控对照实验。  
- **原文链接**：https://www.beryldesign.fr/en/post/liquid-glass-vs-material-3-expressive

### [Does Your Form Really Need a Dropdown List?]
**来源**：Nielsen Norman Group（2026-07-17）｜专家相关：Kate Moran 所在机构 NN/g  
**类型**：专家观点/动态  
**是否与动效相关**：否（表单控件选择；与移动端选择器/Bottom Sheet 动效场景相邻）

**摘要**：专家相关（NN/g）。文章系统拆解下拉列表的发现性、交互成本与可访问性代价，给出「约 5–10 项且次要字段」等窄适用条件，并对照 radio、combobox、地址自动补全等替代。对 AI PM/用研：模型选择器、行业/国家等长列表常被滥用 dropdown，应先做控件决策再谈动效。

**详细展开**  
- **背景与问题**：Dropdown 因省空间、约束输入而滥用，却把选项藏在二次点击后，移动端更易误触关闭与滚动过冲。  
- **主要发现/方法/功能/观点**：选项过少应用 radio；过长应用可过滤 combobox；熟悉数据（年龄/生日）优先键盘输入；需视觉比较的变体（尺码/颜色）应用按钮阵列。引用 GOV.UK、USWDS、Material、Carbon 等阈值阈值。  
- **启示**：移动端「选择器动效」（如本期 Linear 的 sheet 接力）解决的是切换流畅度；若控件类型选错，再丝滑动效也降不了决策成本。用研清单可先问「用户是否必须打开才能知道有什么可选」。本期未检索到 6 位具名专家本人 7 日内新发文，故以机构高质量新文补位。  
- **原文链接**：https://www.nngroup.com/articles/dropdown-list/
